# Phase 01.1: CI pipeline - Research

**Researched:** 2026-09-13
**Domain:** GitHub Actions CI for Node.js TypeScript (vitest, eslint, tsc)
**Confidence:** HIGH

## Summary

Phase 01.1 is a greenfield GitHub Actions setup on top of an already-working Phase 1 scaffold. All four npm scripts (`test`, `lint`, `typecheck`, `build`) pass locally today; the only functional gap is that `typecheck` covers `src/` only because `tsconfig.json` excludes `test/`. The phase closes that gap with `tsconfig.test.json` and a dual-`tsc` `typecheck` script, then wires four parallel CI jobs that each run checkout → setup-node (Node 24, npm cache) → `npm ci` → one npm script.

Locked decisions constrain this to minimum-viable tooling: no Prettier, no pre-commit hooks, no branch-protection docs, no CI badges, no artifact upload. The workflow file should be structured as named top-level jobs (`test`, `lint`, `typecheck`, `build`) so Phase 5 can append a `docker-build` job without restructuring.

**Primary recommendation:** Add `.github/workflows/ci.yml` with four parallel jobs on `ubuntu-latest`, pin `actions/checkout@v7` and `actions/setup-node@v7` with `node-version: 24` and `cache: npm`, use `npm ci`, extend `typecheck` to run both tsconfigs, and document trunk-based development in README (not branch protection).

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Formatting Enforcement
- **D-01:** Stay eslint-only — carry forward Phase 1 decision D-12. No Prettier dependency or `format:check` script.
- **D-02:** No `format:fix` script. Developers rely on editor formatting or manual fixes.
- **D-03:** No git pre-commit hooks (no husky, no lint-staged). CI is the quality gate per OPS-04 minimum-viable tooling.

#### Test File Typechecking
- **D-04:** Add `tsconfig.test.json` extending the base config to include `test/**/*.ts`. Same strict compiler options as `src/`.
- **D-05:** Single `npm run typecheck` command covers both `src/` and `test/` (e.g., `tsc --noEmit -p tsconfig.json && tsc --noEmit -p tsconfig.test.json`, or equivalent project-reference approach).
- **D-06:** Test files use identical strict TypeScript settings to application code — no relaxed rules in `test/`.
- **D-07:** Primary motivation: catch type errors in test helpers and fixture tests before they reach `main`.

#### Workflow Job Layout
- **D-08:** Parallel CI jobs — separate jobs for `test`, `lint`, `typecheck`, and `build`. Clear failure attribution; Phase 5 adds a `docker-build` job alongside without restructuring.
- **D-09:** CI triggers on `push` and `pull_request` targeting `main` only. `pull_request` trigger is configured for future adoption but the team uses trunk-based development with direct pushes to `main` for now.
- **D-10:** Node.js 24 only in CI — matches `engines.node: "24.x"` (Phase 1 D-09). No version matrix.
- **D-11:** Cache npm dependencies via `actions/setup-node` with `cache: npm`. Use `npm ci` (not `npm install`) for reproducible installs from committed `package-lock.json`.

#### Build Step
- **D-12:** Include `npm run build` as a separate parallel CI job now — verifies `tsc` emit to `dist/`, not just `--noEmit` typecheck.
- **D-13:** No `dist/` artifact upload. Build job verifies compilation only; Phase 5 Docker job builds from source.
- **D-14:** Build failure fails the CI workflow the same as test/lint/typecheck. No branch protection rules or required status checks — trunk-based workflow without PRs means merge blocking is not configured.

#### Development Workflow Documentation
- **D-15:** Document trunk-based development in README: direct pushes to `main`, no PR workflow for now, CI runs on every push to `main`. Do not document branch protection setup or CI status badges.

### Pattern 1: Parallel jobs with shared bootstrap

**What:** Four top-level jobs, each independently running checkout → setup-node → npm ci → one script.

**When to use:** Locked by D-08; enables clear GitHub UI failure labels and Phase 5 `docker-build` append.

**Example:**

```yaml
# Source: https://docs.github.com/en/actions/using-workflows/workflow-syntax-for-github-actions
# Source: https://github.com/actions/setup-node/blob/main/README.md
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm test

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run typecheck

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
```

### Pattern 2: Dual tsconfig typecheck

**What:** Keep `tsconfig.json` for `src/` (and build emit). Add `tsconfig.test.json` for `test/` with overridden `rootDir` to avoid TS6059 ("not under rootDir").

**When to use:** Locked by D-04–D-07. Verified locally during research — pattern compiles cleanly.

**Example:**

```json
// tsconfig.test.json — extends base strict config
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "rootDir": ".",
    "noEmit": true
  },
  "include": ["test/**/*.ts"],
  "exclude": ["node_modules", "dist"]
}
```

```json
// package.json script update
"typecheck": "tsc --noEmit -p tsconfig.json && tsc --noEmit -p tsconfig.test.json"
```

**Why `rootDir: "."` override:** Base `tsconfig.json` sets `rootDir: "src"`. Including `test/**/*.ts` without override triggers TS6059. Overriding in the test config only keeps src build config unchanged.

- **Sequential all-in-one job:** Violates D-08; harder to identify which gate failed.
- **YAML anchors / composite actions for 3 setup steps:** Disproportionate for OPS-04; duplicated steps are the community norm for small repos.
- **Matrix over Node versions:** Rejected by D-10; adds runtime without value.
- **Branch protection docs in README:** Conflicts with D-14/D-15 despite ROADMAP success criterion #2 — CONTEXT wins.
- **Uploading `dist/` artifact:** Deferred per D-13; Phase 5 Docker builds from source.
- **`npm install` in CI:** Non-reproducible vs lockfile; use `npm ci` [CITED: github.com/actions/setup-node advanced-usage].

## Common Pitfalls

### Pitfall 1: ROADMAP vs CONTEXT on branch protection

**What goes wrong:** Planner implements ROADMAP success criterion #2 ("branch protection documented in README") and violates D-14/D-15.

**Why it happens:** ROADMAP written before trunk-based workflow decision finalized.

**How to avoid:** Follow CONTEXT.md locked decisions. README documents trunk-based pushes and CI behavior, not branch protection.

**Warning signs:** README mentions "required status checks" or "merge blocking."

### Pitfall 2: Forgetting `rootDir` override in `tsconfig.test.json`

**What goes wrong:** `tsc -p tsconfig.test.json` fails with TS6059 — test files not under `rootDir: "src"`.

**Why it happens:** Extending base tsconfig inherits `rootDir: "src"`.

**How to avoid:** Override `rootDir: "."` and `noEmit: true` in `tsconfig.test.json` (verified in research).

**Warning signs:** Typecheck passes on src-only but fails once test config added.

### Pitfall 3: Local Node 22 vs CI Node 24 drift

**What goes wrong:** Developer on Node 22 sees `EBADENGINE` warnings; CI passes on Node 24.

**Why it happens:** `engines.node: "24.x"` enforced in CI but not locally.

**How to avoid:** Document in README that CI pins Node 24; recommend nvm/fnm for local alignment. Not a CI bug — expected per D-10.

**Warning signs:** Local warnings but green CI; vitest/tsc still run on Node 22 today.

### Pitfall 4: Missing `permissions: contents: read`

**What goes wrong:** Over-broad default token permissions on newer GitHub repos.

**Why it happens:** Omitting explicit permissions block.

**How to avoid:** Add workflow-level `permissions: contents: read` per setup-node/checkout recommendations [CITED: github.com/actions/setup-node].

**Warning signs:** Workflow has implicit write permissions without need.

### Pitfall 5: Assuming eslint covers type safety in tests

**What goes wrong:** eslint `recommended` preset passes but test helpers have type errors.

**Why it happens:** Phase 1 deliberately uses non-typed eslint preset (OPS-04); type safety is tsc's job.

**How to avoid:** Dual tsconfig typecheck (D-05); do not upgrade to `strictTypeChecked` eslint unless explicitly requested.

**Warning signs:** `npm run lint` green but test types wrong.
